# 17. 剩余实验规划：prefill 为主，decode 收尾

日期：2026-10-15。范围不变：Qwen3.6-27B-FP8、固定 vLLM 0.31.0（db9527a4…）、单卡 RTX PRO 6000、FP8 权重、BF16 lm_head（验证侧）、不做 FP4/NVFP4。64K 草稿词表已通过两个时段复测（+13.55% / +13.72%，40 条请求流式/非流式逐 token 一致），暂不放回生产。

## 1. 出发点：19K 冷 prefill 的时间账

数据来自 [mtp4-prefill-r1-analysis.json](evidence/profiling/mtp4-prefill-r1-analysis.json)（18,901 输入 / 1 输出，GPU kernel 合计 2,266.7 ms，捕获跨度 2,286.9 ms）。

| 类别 | 时间 | 占比 | 性质 | 余量判断 |
|---|---:|---:|---|---|
| FP8 GEMM | 1,582 ms | 69.8% | 算力瓶颈 | 已到功耗墙下可用峰值的 ~87%（[16 号任务 A](evidence/sm120-next/a-gemm-ceiling/results/summary.md)），关闭 |
| 全注意力（FlashInfer BatchPrefill，34 次） | 321 ms | 14.2% | 算力瓶颈，随长度平方增长 | 见 §3，估算效率明显低于 GEMM |
| 小算子合计（激活+量化、norm、conv、state copy 等） | 303 ms | 13.4% | 读写显存瓶颈 | 融合可去掉中间结果往返，见 §4 |
| GDN delta-rule（FlashInfer GDN prefill） | 61 ms | 2.7% | — | 已是上游新 kernel，不做 |

两个直接结论：

- **GPU 没有空闲。** kernel busy union / 跨度 = 99.1%（decode 98.7%，DFlash 96.6%）。CPU 调度、kernel launch、CUDA Graph 都不是可挖的方向。
- **能动的只剩三块：** 少算（前缀复用）、注意力 kernel、小算子融合。分块方式（16160 + 2741）是附带诊断。

## 2. P1 前缀复用：命中多少、在哪里断

**为什么可行。** 因果模型里第 i 个 token 的中间结果只依赖它前面的 token，所以相同前缀算出的 KV 与 GDN 状态完全相同，可以存下来直接复用，被复用的部分不用算。已有证据：44K 输入首次 6.18 s，完全相同的重复请求 0.52 s（[01 号](01-server-baseline.md)）。

**为什么不简单。** 两类层的“缓存单位”完全不同：

- 全注意力层：每个 token 一份 KV，16 层 × 2 × 4 KV 头 × 256 维 × 1B（FP8）≈ 32 KB/token，按 block 存，任何 block 对齐的公共前缀都能复用。
- GDN 层：没有逐 token 的 KV，只有一个不断被覆盖的“滚动状态”。48 层 × 48 头 × 128 × 128 ≈ 3,770 万个数，一份快照约 75 MB（BF16）或 151 MB（FP32，存储精度待核实），相当于 2,300–4,700 个 token 的 KV。vLLM 不可能每个 block 都存，只在部分边界存快照；没存快照的位置无法恢复，只能从最近一个快照往后重算。

所以“完全重复命中”不代表“公共前缀命中”。这正是要测的。

**实验。** 固定一份 ~19K 和一份 ~44K 文本，冷启动后依次发：

| 场景 | 请求构造 | 关心什么 |
|---|---|---|
| S1 完全重复 | 同一请求再发一次 | 复核基线（预期接近 0.5 s） |
| S2 公共前缀 + 新尾巴 | 前 15K/40K 相同，尾部 1K–4K 不同 | 命中 token 数是否接近公共前缀长度，还是退回到某个快照点 |
| S3 多轮对话 | 第 2 轮 = 第 1 轮 prompt + 第 1 轮输出 + 新消息 | decode 产生的 token 有没有快照；第 2 轮要重算多少 |
| S4 前缀位置扫描 | 公共前缀长度取 block 边界 ±1、快照间隔的倍数 ±1 | 推出实际快照粒度 |

每个场景记录 `prefix_cache_hits` 增量、TTFT、命中 token 数；MTP4 开/关各一遍（[03 号](03-upstream-research.md)记录的上游 #60533 修过“Mamba prompt checkpoint 与投机解码命中边界不一致”）。

**正确性门槛：** 命中路径与冷路径 greedy 输出逐 token 一致；否则该场景判失败，不讨论速度。

**后续可调项（取决于 S2–S4 结果）：** 快照间隔 / mamba cache 模式等启动参数；快照显存代价与 KV 容量的权衡。只改参数、不改代码。

**预期：** 命中部分几乎不花时间，TTFT ≈ 未命中尾部的计算时间。对冷请求没有帮助。

## 3. P2 注意力：先算效率，再换实现

**为什么可行。** 用模型配置（24 个 Q 头、4 个 KV 头、head_dim 256、16 层）算：因果注意力每层约 12,288 × L² FLOP，18,901 输入时 16 层约 70 TFLOP，321 ms，约 **219 TFLOP/s**。若按 BF16 计算（FP8 KV 反量化后），功耗墙下可用 BF16 峰值约 357 TFLOP/s（713/2），即约 61%，而 GEMM 是 87%。若实际已走 FP8 QK（日志有 q_scale 回落 1.0 的告警，需核实），比例更低。两种情况都说明有空间。

**为什么长输入更重要。** 注意力 ∝ L²，其余 ∝ L。用 19K 的账外推：44K 估 6.27 s（实测 6.18 s，吻合），注意力约 28%；64K 估约 10.6 s，注意力约 36%；128K 估约 29 s，注意力约 53%。

**实验。**

1. 确认实际 kernel 变体与计算精度（FlashInfer 日志、NCU 一次）。
2. 后端 A/B/A：`FLASHINFER` / `FLASH_ATTN` / `TRITON_ATTN`，FP8 KV 不变；输入 19K、44K、64K、128K。只改 `--attention-backend`，其余与 [arm.py](evidence/sm120-next/d-draft-vocab/results/scripts/arm.py) 相同。
3. 胜出者做正确性：D3 16 条 + 24 条扩展请求逐 token 比对；不一致则需长上下文质量回归，不能直接采用。
4. 若 FP8 QK 是可选项且当前未开，单独作为精度变化测试，必须过质量门槛。

**预期：** 19K 冷 TTFT 2–4%；64K 以上更多。

## 4. P3 小算子融合：只融合“轻对轻”

**为什么可行。** 小算子都是读写显存瓶颈：耗时 ≈ 搬运字节 / 1.79 TB/s。M=16,160、K=5,120 的 BF16 激活一份约 165 MB，每多一个独立 kernel 就多一次“写回显存再读出来”。把相邻小算子合成一个，中间结果留在寄存器里，省掉的就是这些往返。

**为什么和 Codex 失败的 epilogue 融合不同。** 那次把激活和量化塞进 GEMM 尾部，GEMM 是算力瓶颈，多出的寄存器和 shared 压力让占 70% 的大核变慢（整模慢 2.6%–7%）。这里只把小核和小核合并，不碰 GEMM。

**候选（来自 kernel 排名）：**

| 候选 | 现状 | 时间 | 做法 |
|---|---|---:|---|
| V2 SiLU×up+量化 | 已有，单时段 TTFT −1.4% | 98 ms 中的一部分 | 跨时段复测，过门槛即可列为候选 |
| 独立 `per_token_group_quant_8bit` | 390 次独立调用 | 35 ms | 先归因来源（GDN 输出 norm、attention 输出、…），融进上游 norm / 门控 kernel |
| GDN gated norm（`layer_norm_fwd_kernel`）+ 后续量化 | 分开两个 kernel | 19 ms + 部分量化 | 合并为 norm+FP8 量化 |
| `_causal_conv1d_fwd` + `_fused_post_conv` | 分开两个 kernel | 25 + 24 ms | 合并为一个 |
| 未融合的 `at::native::elementwise` | 288 次 | 16 ms | 归因后交给 Inductor 或手写合并 |

**门槛：** 每个融合先做逐位数值比对（与原链相同的 BF16 舍入与 per-128 scale），再整模 A/B/A + 逐 token 输出一致。

**预期：** 小算子池共 13.4%，现实可回收约三分之一，19K 冷 TTFT 2–4%（含 V2）。

## 5. P4 分块诊断：为什么是 16160 + 2741

`max_num_batched_tokens=32768`，18,901 输入本可一次算完，但实测分成 16,160 与 2,741 两块。推测与混合模型前缀缓存的块对齐或快照边界有关（16,160 = 16 × 1,010，未核实）。

- 读启动日志里的 block size、mamba cache 模式，确定切分规则。
- 关掉前缀缓存跑一次作为诊断对照，看是否变成一块、TTFT 变化多少。
- 速度预期 <1%：M=2741 的 gate_up 只比按比例折算慢约 4%，且只占 15% 的 token。主要价值是解释 P1 的快照位置。

## 7. 不做的

GEMM 主循环、tile、调度、cuBLASLt（任务 A 已关闭）；GEMM epilogue 融合；CPU/launch/CUDA Graph（GPU 忙碌率 ≥96.6%）；GDN prefill 重写（已是 FlashInfer 新 kernel，占 2.7%）；FP4/NVFP4、lm_head 低精度；DDTree。
