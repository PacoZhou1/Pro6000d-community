# GEMM recovery v1: independent local recomputation

Both GPU jobs exited 0. This review recomputes [M2741](../takeover/gemm-v1/m2741.jsonl) and [M16160](../takeover/gemm-v1/m16160.jsonl) from their JSONL, rather than trusting their printed summaries. Each shape has four numeric gates, four changed-input Graph gates, two full-matrix gates, one changed-input full-matrix PR gate, and 31 complete four-arm randomized pairs in each of warm and cache-disturbed modes. All passed. The script SHA recorded in both files is `2a7c39ed9f669ecdeee815a5be20bad99a854f32393b4cfa4572c182976a8477`; the full recomputation, raw SHA values, build SHAs, and NVML ranges are in [summary.json](summary.json).

The ratio is the **median of 31 ratios within the same randomized pair**. It differs from the ratio of separate arm medians. For example, M2741 warm PR is 1.0418 paired, while `median(CUTLASS)/median(PR)=1.0813`: the run changes speed partway through (around pair 15), so separate medians land on different phases. The paired figure is the controlled comparison. At M16160, warm clock readings span 1950–2745 MHz and power readings 124–553 W; the disturbed window is steadier at 1942–1965 MHz and 553–601 W. At M2741, the short warm Graph intervals often report 2670 MHz and only 81 W, revealing NVML polling lag/idle samples; exact-window samples were present for only 18–26 of 31 per arm. These sensor readings cannot normalize a ~4–6% effect reliably. The disturbed mode writes an owned >2×L2 buffer outside events; it is not proven cold L2. A separate thermally steady repeat could test stability, but cannot turn this result into a 10% win.

The numeric outcome is strong within each scheme. The PR-derived rowwise kernel matches cuBLAS rowwise **bit for bit** over all 95,430,656 BF16 values at M2741 and all 562,626,560 at M16160; it also matches after changed-input Graph replay. MXFP8 versus independently dequantized BF16 A/W and BF16 matmul has full-matrix NRMSE `5.37e-5`/`5.34e-5`, with 23,327/138,247 differing BF16 values and max absolute difference 4/8 respectively. All four arms pass their own sampled FP32 reference, full-output finite check, and changed-input replay reference. This is random-data, single-operator evidence; block128, MXFP8, and rowwise scales have **different semantics**, so the three schemes' speed ratios do not establish interchangeable Qwen weights or model quality. PR weight row reordering and MX scale packing were performed before timing. The PR ABI constructs TMA descriptors on the host per call, but CUDA Event/Graph timing excludes this cost; a separate CPU wall-time dispatch measurement would be needed if revisiting integration.

The fixed [SM120 vLLM dispatch source](../../gemm-targeted/source/csrc/libtorch_stable/quantization/w8a8/cutlass/c3x/scaled_mm_blockwise_sm120_fp8_dispatch.cuh) (SHA256 `8a9ee5dc8edb96bc4619883a6248eb15211fd37db2d3fc02de25c5b02ee5af41`) selects its 128×128×128 Cooperative configuration when M>256, so both baseline shapes are configured for M128 tiles. The compiled MX adapter independently uses M128; the generated PR derivative uses M128 with masked tail. M2741 therefore spans 22 M tiles (last 53 valid rows), and M16160 spans 127 (last 32 valid rows). These are **source/configuration deductions**, not an independently observed grid counter. The `cutlass_m_tile=128` JSON field does not describe cuBLAS's internal tiling, which was not established. As-built MX and PR kernels used 168 and 193 registers/thread, each with zero reported spills ([build logs](../takeover/b-mxfp8-recovery/)); this alone does not explain throughput.

The [before/after service snapshots](../takeover/gemm-v1/services-before.json) passed: original 27B, 9B, and ASR stayed stopped; embedding kept the same container/start time, returned HTTP 200 and a finite 1024-dimensional vector. Its prompt-token and successful-request counters were unchanged at 109,984 and 2,118 around each shape; running/waiting requests remained 0. The [two monitor snapshots](../takeover/gemm-v1/embedding-monitor.jsonl) likewise show healthy service. These observations support a quiet window but cannot rule out sub-snapshot transient activity.

No tested arm reaches the proposed 1.10 same-pair GEMM threshold: the strongest M16160 value is cuBLAS rowwise 1.0619, then PR-derived 1.0487, while MXFP8 is slower than block128. Given different scale semantics and excluded conversion/packing/host setup costs, this operator run alone does not justify model integration. A second stabilized window or host-dispatch probe is useful only to explain the small ~4–6% rowwise advantage, not to claim a demonstrated 10% gain.
